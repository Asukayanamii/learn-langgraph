# 常见问题与排错指南

> 这里收集的**全部是真实踩过的坑**——包括开发这个项目时触发的报错。
> 遇到问题时先在这里搜报错关键词。

## 一、环境与运行问题

### 1.1 `ModuleNotFoundError: No module named 'common'`

**现象**

```
File "lessons/01_basic_chatbot.py", line 30, in <module>
    from common import graph_viz, pretty
ModuleNotFoundError: No module named 'common'
```

**原因**

Python 运行脚本时，只会把**脚本所在的那层目录**加进模块搜索路径。
执行 `python lessons/01_basic_chatbot.py` 时，搜索路径里是 `lessons/`，不是项目根目录。

**解决**

项目已经用 `lessons/_bootstrap.py` 处理了。如果你自己新建文件，在文件开头加一行：

```python
import _bootstrap  # noqa: F401
from common import pretty
```

或者从项目根目录用模块方式运行：

```bash
python -m lessons.lesson01_basic_chatbot     # 注意：文件名不能以数字开头
```

---

### 1.2 `ModuleNotFoundError: No module named 'langgraph'`

说明没装依赖，或者没激活虚拟环境。

```bash
# 确认用的是哪个 Python
python -c "import sys; print(sys.executable)"

# 应该指向项目里的 .venv
# Windows:  .venv\Scripts\python.exe
# macOS/Linux: .venv/bin/python

# 重新安装
pip install -r requirements.txt
```

---

### 1.3 Windows 控制台中文乱码

**现象**：输出里出现 `??????` 或 `UnicodeEncodeError`。

**解决**：项目里的 `common/pretty.py` 已经做了处理（`reconfigure(encoding="utf-8")`）。
如果自己写脚本遇到，可以：

```powershell
# PowerShell 临时设置
$env:PYTHONIOENCODING="utf-8"
$env:PYTHONUTF8="1"
```

或者在代码里：

```python
import sys
sys.stdout.reconfigure(encoding="utf-8")
```

---

### 1.4 输出全是 `[1m[33m` 这样的乱码

这是 ANSI 颜色转义码，说明你的终端不支持颜色。

```powershell
# 关掉颜色
$env:NO_COLOR="1"
```

或者永久设置：Windows Terminal / VS Code 终端一般支持颜色，老版 `cmd.exe` 可能需要
`python -X utf8` 加 `os.system("")`（项目已处理）。

## 二、状态（State）相关错误

### 2.1 `InvalidUpdateError: Can receive only one value per step`

**完整报错**

```
langgraph.errors.InvalidUpdateError: At key 'findings': Can receive only one value per step.
Use an Annotated key to handle multiple values.
```

**原因**：**同一轮超级步里有多个节点写了同一个字段，但那个字段没有 reducer。**

典型场景：

```python
class State(TypedDict):
    findings: list          # ❌ 没有 reducer

builder.add_edge(START, "a")   # a 和 b 并行
builder.add_edge(START, "b")   # 两个都返回 {"findings": [...]}
```

**解决**

```python
class State(TypedDict):
    findings: Annotated[list, operator.add]   # ✅ 加上 reducer
```

**注意一个容易混淆的对比**：

| 场景 | 无 reducer 的结果 |
|---|---|
| 并行写同一字段 | **直接报错**（好事，问题立刻暴露） |
| 串行写同一字段 | **静默覆盖**（危险，可能上线才发现） |

---

### 2.2 `InvalidUpdateError: Expected dict, got ...`

**完整报错**

```
langgraph.errors.InvalidUpdateError: Expected dict, got 我以为我返回了状态更新
```

**原因**：节点函数忘了 `return` 一个字典。

```python
# ❌ 错误
def node(state):
    return "我以为我返回了状态更新"

# ✅ 正确
def node(state):
    return {"messages": [...]}
```

**排查**：检查所有分支是否都有 `return`，以及返回的是不是 `dict`。
特别注意 `return some_list` 或 `return None`（函数没有 return 语句）这两种写法。

---

### 2.3 节点返回了字段，但状态里没有（**静默丢弃，最坑**）

**现象**：不报错、不警告，但数据就是不见了。

```python
class State(TypedDict):
    user_level: str

def node(state):
    return {"user_lvl": "VIP"}     # ← 拼错了！

result = graph.invoke(...)
# result 里没有 user_lvl，也没有任何报错
```

**这是 LangGraph 最危险的一类问题**——因为没有任何提示。

**排查清单**

1. 字段名拼写（`user_lvl` vs `user_level`）
2. 字段是不是没写进 `TypedDict`
3. reducer 函数有没有把值丢掉

**预防**：给节点函数的返回值加类型注解 `-> dict`，用 IDE 的自动补全减少拼写错误。

---

### 2.4 `NameError: name 'operator' is not defined`

**现象**：写自定义 reducer 时报这个错，即使你在函数里 `import operator` 了。

**原因**：`TypedDict` 里的类型注解是**延迟求值**的——

```python
# ❌ 这样不行
def demo():
    import operator                      # ← 局部导入
    class State(TypedDict):
        total: Annotated[int, operator.add]   # LangGraph 建图时解析不到 operator
```

LangGraph 在 `compile()` 时才去解析这些注解，此时函数内部的局部导入早已失效。

**解决**：把 `import operator` 放到**文件顶部**。

```python
import operator          # ✅ 模块级导入
from typing import Annotated, TypedDict
```

## 三、Checkpointer 与中断相关错误

### 3.1 `Checkpointer requires one or more of the following 'configurable' keys: thread_id`

**原因**：图挂了 checkpointer，但调用时没给 `thread_id`。

引擎不知道这轮对话该存到哪个"会话文件夹"里。

**解决**

```python
config = {"configurable": {"thread_id": "user-42"}}
app.invoke(input, config=config)
app.stream(input, config=config)
app.get_state(config)
```

**每个请求都要传**，包括 `invoke`、`stream`、`get_state`、`get_state_history`、`update_state`。

---

### 3.2 中断之后 `Command(resume=...)` 没反应

**排查顺序**

1. **确认有 checkpointer** —— 没有它，中断根本无法保存状态
2. **确认 `thread_id` 一致** —— 恢复时的 `thread_id` 必须和中断时相同
3. **确认是在同一个进程/同一个数据库** —— 用了 `InMemorySaver` 的话，换进程就丢了
4. **确认 `interrupt()` 不在 `try/except` 里** —— 它内部靠抛异常实现，
   被你的 `except` 捕获就失效了

```python
# ❌ 绝对不要这样写
def node(state):
    try:
        answer = interrupt("确认吗？")
    except Exception:
        answer = False        # ← 把中断异常吃掉了，图再也不会暂停
```

---

### 3.3 中断后重放，副作用执行了两次

**这是 `interrupt` 最容易踩的坑。**

**原因**：恢复执行时，节点是**从头重放**的，不是从 `interrupt()` 那行继续。

```python
# ❌ 错误写法
def node(state):
    record_audit_log()              # ← 会被执行两次！
    answer = interrupt("确认吗？")
    do_something()
```

**解决**：把有副作用的代码放到 `interrupt()` **之后**。

```python
# ✅ 正确写法
def node(state):
    answer = interrupt("确认吗？")    # ← 放最前面
    if answer:
        record_audit_log()          # ← 只在恢复后执行一次
        do_something()
```

---

### 3.4 `SqliteSaver` 报线程/连接错误

**原因**：`SqliteSaver` 的连接对象不能被多个线程共用。

**解决**：每个请求开一个连接（用上下文管理器），或者用连接池。

```python
with SqliteSaver.from_conn_string(str(db_path)) as checkpointer:
    app = build_graph(checkpointer=checkpointer)
    ...
```

**生产环境建议直接上 `PostgresSaver`**，天然支持并发。

## 四、循环与死锁

### 4.1 `GraphRecursionError: Recursion limit of 25 reached`

**原因**：图没有终止条件，一直在转。

**排查方向**

| 场景 | 常见原因 | 对策 |
|---|---|---|
| ReAct 循环 | 工具总是报错，模型反复重试 | 工具内部返回错误信息而不是抛异常 |
| 多智能体 | 主管一直派活，不返回 `FINISH` | 状态里记 `done`；提示词写清终止条件 |
| 条件边 | 判断函数永远返回同一个标签 | 检查判断逻辑是否读到了预期的字段 |

**临时放宽**（不推荐当解决方案）：

```python
app.invoke(input, config={"recursion_limit": 50})
```

**正确做法**：先搞清楚"为什么停不下来"。

> 💡 一个诊断技巧：用 `stream_mode="updates"` 跑，把经过的节点打印出来，
> 你能立刻看到它在哪两个节点之间来回转。

## 五、工具与消息协议

### 5.1 `messages with role 'tool' must be a response to a preceding message with tool_calls`

**原因**：`AIMessage` 里有 `tool_calls`，但后面没有对应的 `ToolMessage`。

**典型场景**：
- 自己筛选了要执行的工具，漏掉了一部分
- 人工拒绝后直接跳过，没补 `ToolMessage`

**解决**：每个 `tool_call_id` 都要有对应的 `ToolMessage`。

```python
for call in last_message.tool_calls:
    outputs.append(ToolMessage(content=..., tool_call_id=call["id"], name=call["name"]))
```

拒绝场景的正确写法（第 04 课）：

```python
reject_messages = [
    ToolMessage(
        content="【人工审批未通过】用户拒绝执行，请不要重试。",
        tool_call_id=call["id"],
        name=call["name"],
    )
    for call in risky_calls
]
```

---

### 5.2 模型不调用工具 / 总是调用错的工具

**排查清单**

1. **docstring 写清楚了吗？** 这是模型唯一的判断依据

   ```python
   # ❌ 模型不知道什么时候用
   def process(data: str) -> str:
       """处理数据。"""

   # ✅ 说清"做什么"和"什么时候用"
   def get_weather(city: str) -> str:
       """查询指定城市的天气。当用户问天气、气温、是否下雨时使用。"""
   ```

2. **`bind_tools` 了吗？**

   ```python
   llm_with_tools = llm.bind_tools(TOOLS)    # ← 别忘了这行
   response = llm_with_tools.invoke(messages)
   ```

3. **`ToolNode` 和 `bind_tools` 用的是同一批工具吗？**

   ```python
   builder.add_node("tools", ToolNode(TOOLS))     # 执行用这批
   llm_with_tools = llm.bind_tools(TOOLS)         # 声明用这批
   # 两批不一致 → 模型要求调一个 ToolNode 里没有的工具
   ```

4. **工具太多？** 超过 10 个就容易互相干扰，考虑拆分或精简。

5. **用的是离线模拟模型？** 它靠关键词匹配，用词太偏可能匹配不上。
   换真实模型，或者用更直白的问法。

---

### 5.3 工具执行报错，整个图挂了

**原因**：工具内部抛异常，没有捕获。

**解决**：工具应该**返回**错误信息，而不是**抛出**异常。

```python
@tool
def calculator(expression: str) -> str:
    """计算数学表达式。"""
    try:
        return str(eval(expression))          # noqa: S307
    except Exception as exc:
        return "计算出错：%s" % exc            # ✅ 返回错误，让模型知道并调整
```

这样模型看到"计算出错"后，还能换个方式重试，而不是整个流程中断。

## 六、性能与成本

### 6.1 运行很慢

| 可能原因 | 排查方法 |
|---|---|
| 节点被串行执行，本来能并行 | 用 `stream_mode="updates"` 看执行顺序 |
| 工具里有慢接口 | 在每个工具里打时间戳 |
| 多智能体轮次过多 | 打印每轮的主管决策 |
| 离线模型的打字延迟 | 设 `OFFLINE_STREAM_DELAY=0` |

**验证是否真并行**：让两个节点各 `time.sleep(0.3)`，量总耗时。
约 0.3 秒 = 并行；0.6 秒以上 = 串行。

### 6.2 Token 消耗比预期高

**最常见的三个原因**

1. **多智能体**：每个专家每次调用都带着完整历史，轮次多了是平方级增长
   → 给专家传摘要，或用 `Send` 只传需要的片段

2. **`messages` 无限增长**：对话越长，每次请求带的上下文越多
   → 加历史裁剪或摘要压缩

3. **工具返回结果太长**：一大段 JSON 全塞进消息里
   → 工具只返回关键字段，或做截断

**诊断工具**：配置 LangSmith（见 `.env.example`），能看到每次调用的完整 token 统计。

## 七、想接真实大模型

### 7.1 怎么配

```bash
# 复制配置模板
copy .env.example .env        # Windows
cp .env.example .env          # macOS / Linux
```

然后编辑 `.env`：

```ini
LLM_PROVIDER=custom
LLM_API_KEY=你的key
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat
```

**支持任何 OpenAI 兼容接口**：DeepSeek、Moonshot、通义千问、智谱、本地 Ollama……

### 7.2 常见报错

| 报错关键词 | 原因 | 解决 |
|---|---|---|
| `AuthenticationError` / 401 | Key 不对 | 检查 `LLM_API_KEY` |
| `NotFoundError` / 404 | `base_url` 或模型名不对 | 查服务商文档，注意别漏 `/v1` |
| `RateLimitError` / 429 | 触发限流 | 降低频率或充值 |
| `Connection error` | 网络不通 / 需要代理 | 检查网络，或用本地 Ollama |
| `model does not support tool calling` | 模型不支持工具调用 | 换一个支持 function calling 的模型 |

### 7.3 怎么确认配置生效了

```bash
python lessons/01_basic_chatbot.py
```

输出里会打印当前模型。如果显示的还是"离线模拟模型"，说明配置没读到：

- `.env` 文件是不是放在**项目根目录**（和 `README.md` 同级）
- 变量名有没有拼错
- 文件名是不是 `.env.txt`（Windows 常见问题，记得开"显示文件扩展名"）

## 八、调试技巧

### 8.1 三个必备的观察手段

```python
# ① 看执行了哪些节点、各改了什么
for event in app.stream(input, config=config, stream_mode="updates"):
    print(event)

# ② 看状态是怎么一步步长大的
for snapshot in app.stream(input, config=config, stream_mode="values"):
    print(snapshot)

# ③ 看当前停在哪儿（中断排查必备）
snapshot = app.get_state(config)
print("next =", snapshot.next)          # 接下来要执行谁；为空说明跑完了
print("values =", snapshot.values)
print("tasks =", snapshot.tasks)        # 里面有 interrupts 信息
```

### 8.2 看图的完整历史

```python
for s in app.get_state_history(config):
    print(s.metadata.get("step"), s.values.get("messages", [])[-1:], s.next)
```

出问题时，能一眼看出"是在哪一步开始不对的"。

### 8.3 打开 LangSmith 追踪

配置 `.env` 里的 `LANGCHAIN_TRACING_V2` 和 `LANGCHAIN_API_KEY`，
每次运行都会在网页上生成完整的调用链路，包括：
每个节点的输入输出、每次模型调用的完整 prompt、token 消耗、耗时。

**这是排查"模型为什么这么回答"的最强工具。**

### 8.4 用 `print` 也有技巧

```python
def node(state):
    print("【进入 node】")
    print("  收到的 messages 条数:", len(state["messages"]))
    print("  最后一条:", type(state["messages"][-1]).__name__)

    result = do_something()

    print("【离开 node】返回:", result)
    return result
```

**特别有用的一招**：在节点里打印 `state` 的 `keys()`，
能立刻发现"我以为状态里有某个字段，其实没有"。

## 十、还是解决不了？

1. **先跑一遍 `python verify_all.py`**，确认是环境问题还是你的代码问题
2. **看一眼图的完整历史**：`app.get_state_history(config)`
3. **用最小可复现例子**：把出问题的部分单独抽出来跑（第 10 课的手写版很适合做这个）
4. **查官方文档**：
   - LangGraph：[langgraph.com.cn](https://langgraph.com.cn)
   - 错误码索引：LangGraph 的报错信息里通常带一个文档链接，直接点进去
5. **打开 LangSmith**，看完整调用链——大多数"模型为什么这么答"的问题都能在这里找到答案
