## 一、消息：Agent 世界的通用货币

### 1.1 四种角色

`messages` 列表里装的全是消息对象，一共四种：

| 类型 | 谁说的 | 关键字段 | 作用 |
|---|---|---|---|
| `SystemMessage` | 开发者 | `content` | 设定人设、规则、约束 |
| `HumanMessage` | 用户 | `content` | 用户输入 |
| `AIMessage` | 模型 | `content`、`tool_calls` | 模型的回复，或"要求调用工具" |
| `ToolMessage` | 你的代码 | `content`、`tool_call_id`、`name` | 工具的执行结果 |

### 1.2 一条消息对象长什么样

```python
AIMessage(
    content="",                                   # 文本内容（要调工具时通常为空）
    tool_calls=[                                  # ★ 模型的"行动请求"
        {
            "name": "get_weather",
            "args": {"city": "北京"},
            "id": "call_abc123",                  # 这次调用的唯一编号
            "type": "tool_call",
        }
    ],
    response_metadata={"model": "gpt-4o"},        # 服务端返回的元数据
    usage_metadata={"input_tokens": 42, "output_tokens": 18},
)
```

```python
ToolMessage(
    content="北京：晴，25℃",                        # 工具的执行结果
    tool_call_id="call_abc123",                   # ★ 必须对应上面那个 id
    name="get_weather",
)
```

## 二、最关键的一节：模型到底怎么"调用"工具的

### 2.1 一个必须破除的误解

**模型永远不会执行你的代码。它只是输出了一段结构化的 JSON。**

```
    你脑子里的模型：                        实际上的模型：
    ┌──────────────────┐                  ┌──────────────────────────┐
    │  "我要调用        │                  │  输出一段文本：            │
    │   get_weather    │                  │  {"name": "get_weather", │
    │   函数"           │                  │   "args": {"city":"北京"}}│
    └────────┬─────────┘                  └──────────┬───────────────┘
             │                                       │
             ▼                                       ▼
        它碰不到你的函数                        执行这段 JSON 的是**你的代码**
```

这个区别极其重要，因为它意味着：

- **安全责任在你。** 模型说"删掉数据库"，你不执行，它就删不掉。
- **权限控制在你。** 你只把想给它用的工具 `bind_tools` 进去。
- **这就是第 04 课 `interrupt` 能成立的根本原因。**

### 2.2 完整的四步流程

```
  ① 你：bind_tools([get_weather, calculator])
     ↓
     把这三个东西随请求一起发给模型：
        · 工具名      "get_weather"
        · 工具描述    "查询指定城市的天气…"
        · 参数结构    {"city": {"type": "string", "description": "城市名称"}}

  ② 模型：阅读用户问题 + 工具说明书
     ↓
     决定：这个问题需要 get_weather，参数是 {"city": "北京"}
     输出：AIMessage(content="", tool_calls=[{name, args, id}])
     ★ 到此为止，模型的工作结束了。它只是"提了个要求"。

  ③ 你的代码（或 ToolNode）：真正执行
     ↓
     按 name 找到工具 → 把 args 当参数传进去 → 拿到返回值
     包装成 ToolMessage(content=结果, tool_call_id=id)

  ④ 把 ToolMessage 追加进 messages，再问一次模型
     ↓
     模型这次看到了工具结果，于是生成自然语言回答
```

**这四步走完，就叫一轮 ReAct。**

### 2.3 为什么 `tool_call_id` 是必须的

因为模型可能**一次要求调用多个工具**：

```python
AIMessage(tool_calls=[
    {"name": "get_weather", "args": {"city": "北京"}, "id": "call_1"},
    {"name": "get_weather", "args": {"city": "上海"}, "id": "call_2"},
])
```

返回时只有靠 `id` 才能分清哪个结果对应哪个请求：

```python
ToolMessage(content="北京：晴", tool_call_id="call_1")   # ← 必须对上
ToolMessage(content="上海：雨", tool_call_id="call_2")
```

**协议规则：模型发了一条带 N 个 tool_calls 的消息，后面就必须跟齐 N 个 ToolMessage。**

漏了会怎样？真实的 OpenAI / Anthropic 接口会直接返回 400 错误。第 10 课有这段错误复现。

> 💡 这也解释了第 04 课的一个细节：用户拒绝了工具调用之后，
> 我们**伪造**了一条"被拒绝"的 ToolMessage。不是为了骗模型，
> 而是为了让消息历史符合协议——否则下一轮请求根本发不出去。

## 三、`add_messages` 到底做了什么

`add_messages` 是 `messages` 字段的标准 reducer。它的行为比"追加"要精细：

```python
def add_messages(left: list, right: list) -> list:
    # 简化版逻辑
    result = list(left)
    for msg in right:
        if msg.id and msg.id in {m.id for m in result}:
            # ① 如果消息自带 id，且列表里已有同 id 的消息 → 更新它
            replace(result, msg)
        else:
            # ② 否则 → 追加
            result.append(msg)
    return result
```

三个实际影响：

| 行为 | 什么时候有用 |
|---|---|
| 追加新消息 | 绝大多数情况 |
| 按 `id` 去重更新 | 流式场景：先插入一条占位消息，后续不断更新它 |
| 支持传入 `{"role": "user", "content": "..."}` 这种字典 | 写起来方便，会自动转成 `HumanMessage` |

最后一点很实用——所以你可以写：

```python
graph.invoke({"messages": [{"role": "user", "content": "你好"}]})
```

而不必显式 `HumanMessage(content="你好")`。

## 四、ReAct 循环：为什么需要"回环边"

### 4.1 从结构上看

```
                    ┌──────────────────────┐
                    │   agent 节点          │
                    │   （大脑：做决策）      │
                    └──────────┬───────────┘
                               │
                  有没有 tool_calls？
                     ┌─────────┴─────────┐
                    有                    没有
                     │                     │
                     ▼                     ▼
          ┌──────────────────┐           END
          │   tools 节点      │        （答完了，收工）
          │  （手脚：执行工具） │
          └────────┬─────────┘
                   │
                   └──────► 回到 agent
```

**那条从 `tools` 回到 `agent` 的边，就是 Agent 的灵魂。**

没有它，图就是一条直线：模型说"我要调工具" → 工具执行完 → 图结束 →
**模型永远看不到工具的执行结果**，自然也就没法回答用户。

### 4.2 从消息流上看

```
    [HumanMessage("北京天气")]
              ↓
    [AIMessage(tool_calls=[get_weather])]        ← 第 1 轮：模型要求调工具
              ↓
    [ToolMessage("北京：晴，25℃")]                ← 你的代码执行了工具
              ↓
    [AIMessage("北京今天晴，25℃")]                ← 第 2 轮：模型看到结果，给出回答
              ↓
             结束（这条消息没有 tool_calls）
```

**循环的退出条件：模型输出的消息里不再有 `tool_calls`。**

这也意味着：**如果模型一直要求调工具，循环就不会停。** 所以需要 `recursion_limit` 兜底（第 09 课有演示）。

### 4.3 用纯 Python 写出来是这样

第 10 课我们会手写一遍，这里先给个预告：

```python
messages = [HumanMessage("北京天气")]

while True:
    reply = llm_with_tools.invoke(messages)      # ① 问模型
    messages.append(reply)

    if not reply.tool_calls:                      # ② 没有工具调用 → 结束
        return reply.content

    for call in reply.tool_calls:                 # ③ 有 → 执行工具
        result = TOOL_REGISTRY[call["name"]].invoke(call["args"])
        messages.append(ToolMessage(result, tool_call_id=call["id"]))
```

**这就是第 02 课那张图的全部内容。** LangGraph 做的事情，是把这段循环变成
可持久化、可中断、可观察、可并行的工程结构。

## 五、`ToolNode` 与 `tools_condition` 的实现

### 5.1 `ToolNode` 做了什么

```python
# 它的核心逻辑，大概就这么长
class ToolNode:
    def __call__(self, state):
        last = state["messages"][-1]
        outputs = []
        for call in last.tool_calls:              # ① 读模型的请求
            tool = self.tools_by_name[call["name"]]  # ② 按名字查表
            result = tool.invoke(call["args"])       # ③ 执行
            outputs.append(ToolMessage(              # ④ 包装成 ToolMessage
                content=result,
                tool_call_id=call["id"],
                name=call["name"],
            ))
        return {"messages": outputs}
```

官方实现额外做了这些：并发执行多个工具、错误捕获与重试、
注入运行时上下文（`InjectedState` 等）、大批量结果落盘。

### 5.2 `tools_condition` 做了什么

```python
def tools_condition(state) -> str:
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "tools"       # 默认标签
    return "__end__"
```

就是一个三行的判断函数。**条件边没有任何魔法，它只是"一个返回字符串的函数 + 一张映射表"。**

### 5.3 两者合起来 = ReAct

```python
builder.add_node("agent", agent_node)
builder.add_node("tools", ToolNode(TOOLS))
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", tools_condition, {"tools": "tools", "__end__": END})
builder.add_edge("tools", "agent")        # ← 回环边
```

这八行代码是所有 LangGraph Agent 的骨架。你以后看到再复杂的 Agent，都能拆回这八行。

## 六、工具设计的实战要点

### 6.1 docstring 是给模型看的接口文档

模型**唯一**能了解工具用途的渠道就是 `name` + `description` + 参数结构。

```python
# ❌ 差的写法：模型不知道什么时候该用它
@tool
def process(data: str) -> str:
    """处理数据。"""

# ✅ 好的写法：说清"做什么"+"什么时候用"
@tool
def search_knowledge(query: str) -> str:
    """查询公司内部知识库，获取售后政策、保修规定、发票、会员权益等资料。

    当用户询问公司规定、退换货政策、产品资料时使用。

    Args:
        query: 要查询的问题或关键词。
    """
```

第 02 课的动手练习②就是让你故意把 docstring 改含糊，观察模型选错工具——
这个体感比看十遍说明都深刻。

### 6.2 工具太多会让效果变差

工具数量增加时，模型的选错概率会明显上升（每个工具都是提示词里的一个干扰项）。

这也正是**多智能体（第 09 课）存在的理由之一**：与其把 20 个工具塞给一个 Agent，
不如拆成"研究员（5 个检索工具）+ 写作员（3 个排版工具）+ 分析师（4 个数据工具）"。

### 6.3 危险工具必须单独标识

```python
DANGEROUS_TOOLS = {"send_email", "delete_account", "transfer_money"}
```

```python
# 第 04 课 / 实战项目里的做法：在 agent 和 tools 之间插一道闸门
builder.add_conditional_edges("agent", tools_condition, {"tools": "approval", "__end__": END})
builder.add_conditional_edges("approval", route, {"tools": "tools", "agent": "agent"})
```

## 七、小结

| 概念 | 要点 |
|---|---|
| 四种消息 | System / Human / AI / Tool，各司其职 |
| `tool_calls` | 模型输出的**行动请求**，不是执行 |
| 谁在执行 | **你的代码**（或 `ToolNode`）在执行 |
| `tool_call_id` | 关联"请求"与"结果"的凭证，协议强制要求 |
| `add_messages` | 追加 + 按 id 去重更新 |
| ReAct 循环 | agent ⇄ tools 的回环边；退出条件是"没有 tool_calls" |
| `ToolNode` | 查表 → 执行 → 包装成 `ToolMessage` |
| `tools_condition` | 三行判断函数，仅此而已 |
