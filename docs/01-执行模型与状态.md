# 原理篇（一）：图的执行模型与状态

> 对应课程：**第 01 课**、**第 05 课**、**第 07 课**
>
> 这篇文档回答一个根本问题：**当你调用 `graph.invoke()` 时，LangGraph 内部到底发生了什么？**

---

## 一、先看一段"如果一个实习生来实现 LangGraph"

要理解设计，最好的办法是先想想"不用它该怎么写"。

```python
# 假设我们要实现一个"图执行引擎"的最简版本
def run_graph(nodes, edges, state):
    current = "START"
    while current != "END":
        node_fn = nodes[current]              # 1. 找到当前节点
        update = node_fn(state)               # 2. 执行，拿到它返回的更新
        state = merge(state, update)          # 3. 把更新合并进状态
        current = edges[current](state)       # 4. 决定下一步去哪
    return state
```

**就这四步。** LangGraph 的核心也就是这四步，只是每一步都做得更严谨：

| 上面这行 | LangGraph 里对应的机制 | 严谨在哪 |
|---|---|---|
| `nodes[current]` | 节点注册表 | 支持重名检测、编译期校验、可视化 |
| `node_fn(state)` | 节点函数 | 支持同步/异步、重试、缓存、回调和流式 |
| `merge(state, update)` | **通道（Channel）+ reducer** | 每个字段有自己的合并规则，且能检测冲突 |
| `edges[current](state)` | 普通边 / 条件边 | 支持多目标（并行）、动态分发（`Send`） |

下面逐个拆开讲，重点在**第 3 步**——它是最容易出错、也最能体现设计功底的地方。

## 二、节点函数的契约：为什么必须"返回增量"

```python
# ✅ 正确写法
def node(state):
    return {"messages": [response]}   # 返回"我要更新什么"

# ❌ 错误写法
def node(state):
    state["messages"].append(response)
    return state                        # 直接改了传进来的状态再返回
```

为什么不允许第二种？

1. **并行时会互相踩踏。** 同一轮里两个节点都在改 `state` dict，结果不可预测。
2. **无法做持久化和回放。** 引擎需要在每一步之后知道"变化量"，才能存快照。
3. **无法做冲突检测。** 如果两个节点都改了同一个字段，只有"返回增量"才能发现。

所以记住这条契约：**节点是无副作用的纯函数，输入状态，输出更新。**

## 三、状态合并的核心：通道与 Reducer

### 3.1 状态不是"一个字典"，而是"一组通道"

这是理解 LangGraph 最关键的一步。

当你写下：

```python
class State(TypedDict):
    messages: Annotated[list, add_messages]
    total: Annotated[int, operator.add]
    user_name: str
```

LangGraph 在 `compile()` 时并不是简单地把 `State` 存起来，而是**为每个字段创建一个"通道"（Channel）**：

```
    State 定义                         编译后生成的通道
    ─────────────────────────         ──────────────────────────────────────
    messages: Annotated[list,          ┌──────────────────────────────────┐
                add_messages]     ──▶  │ BinaryOperatorAggregate           │
                                       │ 合并函数 = add_messages            │
                                       │ 当前值   = [...]                   │
                                       │ 版本号   = 7                       │
                                       └──────────────────────────────────┘

    user_name: str               ──▶   ┌──────────────────────────────────┐
                                       │ LastValue                         │
                                       │ 合并函数 = 直接覆盖                 │
                                       │ 当前值   = "小明"                  │
                                       └──────────────────────────────────┘
```

LangGraph 内部主要有三类通道：

| 通道类型 | 什么时候用 | 合并行为 |
|---|---|---|
| `LastValue` | 字段没有标注 reducer | 新值覆盖旧值 |
| `BinaryOperatorAggregate` | 字段标注了 `Annotated[X, fn]` | 调用 `fn(旧值, 新值)` |
| `Topic` | 内部用于 `Send` 分发等场景 | 收集多个值 |

**关键洞察：所谓 reducer，其实就是这个通道上的"合并函数"。** 它不是 LangGraph 发明的语法糖，而是执行模型必需的组成部分。

### 3.2 合并发生在什么时候

每一轮超级步结束后，引擎做一次统一合并：

```
    超级步 N 执行完毕，收到各节点返回的更新：

        node_a 返回 {"total": 1, "user_name": "A"}
        node_b 返回 {"total": 2, "tags": ["x"]}

                        ↓ 引擎开始合并                        ↓

    ┌──────────────┬──────────────────┬─────────────────────────────┐
    │ 通道          │ 收到的更新         │ 合并结果                     │
    ├──────────────┼──────────────────┼─────────────────────────────┤
    │ total        │ [1, 2]            │ operator.add(0, 1, 2) = 3   │
    │ user_name    │ ["A"]             │ "A"（只有一个，直接写入）      │
    │ tags         │ [["x"]]           │ merge([], ["x"]) = ["x"]    │
    └──────────────┴──────────────────┴─────────────────────────────┘
```

### 3.3 冲突检测：为什么并行时不加 reducer 会报错

如果 `total` 是 `LastValue` 通道，而同一轮里两个节点都写了它：

```
    node_a 返回 {"total": 1}
    node_b 返回 {"total": 2}
                    ↓
    InvalidUpdateError: At key 'total': Can receive only one value per step.
                        Use an Annotated key to handle multiple values.
```

引擎的道理很简单：**它不知道该保留哪一个。** 与其猜一个然后让 bug 潜伏到线上，不如直接报错。

这解释了第 07 课的那个实验：

- **并行** + 无 reducer → **报错**（好事，问题立刻暴露）
- **串行** + 无 reducer → **静默覆盖**（危险，问题可能上线才发现）

### 3.4 自己写 reducer 要注意什么

```python
def merge_unique(old: list, new: list) -> list:
    result = list(old or [])          # ① 必须容忍 None
    for item in new or []:
        if item not in result:
            result.append(item)
    return result
```

两个坑：

1. **必须能处理 `None`。** 字段第一次被写入时，通道里可能还没有值。
2. **必须是纯函数。** 不能依赖外部变量——因为图可能被**重放**（第 04、08 课会讲），
   重放时外部状态可能已经变了，但你的 reducer 必须给出同样的结果。

## 四、超级步（Superstep）：并行的边界

这是 LangGraph 执行模型里第二重要的概念。

### 4.1 什么是超级步

LangGraph 借鉴了 Google Pregel 图计算模型的思路，把执行切成一轮一轮：

```
    超级步 1:  执行所有"被激活"的节点 → 收集它们的更新 → 合并
    超级步 2:  用合并后的状态，执行下一批被激活的节点 → 收集 → 合并
    ...
    直到没有节点被激活
```

### 4.2 一条规则，解释三种现象

由超级步的定义可以直接推出：**同一轮里的节点读到的都是"本轮开始时"的状态。**

这一条规则解释了三个让人困惑的现象：

**现象 1：并行分支看不到彼此的结果**

```python
builder.add_edge(START, "a")     # a 和 b 在同一轮
builder.add_edge(START, "b")
```

`a` 改了 `user_name`，`b` 在自己的代码里读 `state["user_name"]` —— 读到的是**旧值**。
因为 `b` 拿到的 state 是这一轮开始时的快照。

**现象 2：必须靠 reducer 来合并**

既然同一轮里的多个节点各自产生更新，而它们又都要写回状态，就必然需要一个合并规则。

**现象 3：汇聚节点要等所有人都完成**

```python
builder.add_edge("a", "summarize")
builder.add_edge("b", "summarize")
```

`summarize` 会在**下一轮**才执行。此时 `a` 和 `b` 的更新都已经合并进状态了，
所以 `summarize` 能同时看到两者的结果。这就是它天然的"屏障"语义。

### 4.3 用一张时间线图看

```
时间 ──────────────────────────────────────────────────────────────▶

超级步 1     [ a ] ─┐                        a 和 b 并行执行
             [ b ] ─┤                        各自读取"初始状态"
                    │
             状态合并 │                        a、b 的更新被 reducer 合并
                    ▼
超级步 2     [ summarize ]                    summarize 读到合并后的状态
                    │
                    ▼
                 END
```

## 五、图的结构元素速查

### 5.1 三种边

```python
# ① 普通边：无条件跳转
builder.add_edge("a", "b")

# ② 条件边：由函数决定去哪
builder.add_conditional_edges(
    "router",                        # 从哪个节点出发
    classify,                        # 判断函数：state -> 标签
    {"sales": "sales", "tech": "tech"},  # 标签 -> 目标节点
)

# ③ 多目标边：一个节点连出多条 → 并行
builder.add_edge(START, "a")
builder.add_edge(START, "b")
```

### 5.2 两个虚拟节点

| 名字 | 常量 | 含义 |
|---|---|---|
| `__start__` | `START` | 图的入口。指向谁，谁先执行 |
| `__end__` | `END` | 图的出口。走到这里，图结束 |

它们只是结构标记，不会被执行。

### 5.3 一个节点没有出边会怎样

会被自动连到 `END`。这在单节点图里很方便，但**多分支图里是隐患**——
你以为它结束了，其实它可能只是"没接完"。建议显式写 `add_edge("node", END)`。

## 六、`compile()` 到底做了什么

很多人以为 `compile()` 是"把 Python 编译成机器码"，完全不是。它做的是：

```
    compile()
       │
       ├─ 1. 校验图结构
       │      · 每个节点是否都能到达 END？（有没有死胡同）
       │      · 有没有孤儿节点？
       │      · 节点名有没有重复？
       │
       ├─ 2. 构建通道
       │      遍历 State 的每个字段，按注释创建对应的 Channel 实例
       │
       ├─ 3. 挂载运行时能力
       │      · checkpointer   → 每步之后存快照
       │      · store          → 长期记忆
       │      · interrupt_before/after → 静态断点
       │      · cache          → 节点级缓存
       │
       └─ 4. 返回 CompiledStateGraph
              一个可执行对象，有 invoke / stream / get_state 等方法
```

**所以 `compile()` 是"组装完成"的标记**——所有运行时能力都在这一步挂上去。
这也解释了为什么"加记忆"只要改 `compile()` 那一行：

```python
app = builder.compile()                     # 没记忆
app = builder.compile(checkpointer=saver)   # 有记忆
```

**图的结构一点都没变，变的只是运行时配置。**

## 七、小结

| 概念 | 一句话解释 |
|---|---|
| 节点契约 | 输入 state，输出"更新字典"，不要改原状态 |
| 通道 Channel | 状态里每个字段在内部都是一个独立的通道 |
| Reducer | 通道上的合并函数：`(旧值, 新值) -> 合并值` |
| 无 reducer | 就是 `LastValue` 通道 → 覆盖 |
| 超级步 | 一轮执行；同轮节点并行，且互相看不到对方 |
| 并行冲突 | 同一轮两个节点写同一个非 reducer 字段 → 直接报错（这是保护） |
| `compile()` | 校验结构 + 建通道 + 挂载运行时能力 |
