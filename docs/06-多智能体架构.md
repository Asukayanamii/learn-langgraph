# 原理篇（六）：多智能体架构与选型

> 对应课程：**第 09 课**
>
> 这篇文档回答：**什么时候该用多智能体？有哪些主流拓扑？各自怎么实现？**

---

## 一、先问：真的需要多智能体吗

多智能体不是"更高级"，它是有代价的：

| 代价 | 说明 |
|---|---|
| Token 消耗成倍增加 | 每个专家的每次调用都带着完整对话历史 |
| 延迟变高 | 主管决策 + 专家执行，串行环节变多 |
| 调试变难 | 出问题时要在多个 Agent 之间找原因 |
| 可能不收敛 | 主管一直派活，永远不 FINISH |

**所以先试试这些更简单的方案：**

```
    问题：工具太多，模型老选错
        → 先试：精简工具、改进 docstring、用 Send 动态分发
        → 还不行：再考虑按工具域拆分专家

    问题：提示词太长，什么都交代不清
        → 先试：拆成多个节点（每个节点一个职责），仍是单 Agent
        → 还不行：再考虑多智能体

    问题：任务需要不同"人设"
        → 先试：不同节点用不同 SystemMessage（这不算多智能体）
        → 还不行：再考虑
```

**判断标准**：如果各环节之间需要**动态决定下一步找谁**，那才值得上多智能体。
如果顺序是固定的，用第 07 课的并行/串行就够了。

## 二、四种主流拓扑

### 2.1 网络式（Network）

智能体之间可以**直接互相交接**，没有中心调度。

```
        ┌───────┐  handoff  ┌───────┐
        │  A    │──────────▶│  B    │
        │      │◀──────────│       │
        └───┬───┘           └───┬───┘
            │                   │
            └───────▶ C ◀───────┘
```

**实现**：用 `Command(goto="目标节点")` 在节点内直接指定下一个执行者。

```python
def agent_a(state):
    ...
    return Command(goto="agent_b", update={"messages": [...]})
```

**特点**：灵活，但**容易失控**（谁都可以跳到谁那里，路径不可预测）。
**适用**：角色边界模糊、需要自由讨论的场景（如头脑风暴、辩论）。

### 2.2 主管式（Supervisor）← 最常用

一个中心主管负责调度，专家只干活不决策。

```
                     ┌──────────────┐
                     │  supervisor  │◀─────────┐
                     └──────┬───────┘          │
          ┌─────────────┬───┴───────┐          │
          ▼             ▼           ▼          │
    ┌──────────┐  ┌──────────┐  ┌────────┐     │
    │researcher│  │  writer  │  │ FINISH │     │
    └────┬─────┘  └────┬─────┘  └───┬────┘     │
         └─────────────┴────────────┘          │
                       │                        │
                       └────────────────────────┘
```

**实现**（第 09 课）：

```python
class Route(BaseModel):
    next: Literal["researcher", "writer", "FINISH"]
    reason: str

def supervisor_node(state):
    router = llm.with_structured_output(Route)
    decision = router.invoke([SystemMessage(SUPERVISOR_PROMPT)] + state["messages"])
    return {"next": decision.next, "done": [...]}

builder.add_conditional_edges("supervisor", route, {
    "researcher": "researcher", "writer": "writer", "FINISH": "finish",
})
builder.add_edge("researcher", "supervisor")   # 干完回主管
builder.add_edge("writer", "supervisor")
```

**特点**：路径可控、易调试、易加终止条件。**绝大多数场景选它。**

**关键技巧**：
- 用 `Literal` 把可选项限死（`with_structured_output`）
- 状态里加 `done` 字段记录"谁干过了"，否则主管会重复派活
- 提示词里写清"什么算完成"

### 2.3 层级式（Hierarchical Teams）

主管下面还有主管。

```
                     ┌─────────────────┐
                     │  顶层 supervisor │
                     └────────┬────────┘
                    ┌─────────┴─────────┐
                    ▼                   ▼
            ┌──────────────┐    ┌──────────────┐
            │ 研究组 supervisor│    │ 写作组 supervisor│
            └───────┬──────┘    └───────┬──────┘
                 ┌──┴──┐              ┌──┴──┐
                 ▼     ▼              ▼     ▼
              [搜索] [分析]        [起草] [润色]
```

**实现**：把"组"做成子图（第 08 课），顶层主管调度子图。

```python
research_team = build_research_team().compile()   # 本身就是一个 supervisor 图
builder.add_node("research_team", research_team)  # 再当节点挂到顶层
```

**适用**：任务规模大到需要分层管理（比如"写一份行业报告"→ 多个调研小组 + 多个写作小组）。

### 2.4 流水线（Sequential Pipeline）

固定顺序，没有调度器。

```
    [研究员] ──▶ [写作者] ──▶ [审校] ──▶ END
```

**这其实不算多智能体**，就是多个节点串联。但它常常是**最稳、最省钱**的方案。
如果顺序是确定无疑的，别为了"架构好看"引入主管。

## 三、Supervisor 模式的实现细节

### 3.1 主管的提示词怎么写

```python
SUPERVISOR_PROMPT = """你是一个调度主管，负责把任务分配给合适的专家，自己不要动手做事。

你的团队：
  - researcher：负责查资料、调研、核实信息
  - writer     ：负责把材料整理成报告

规则：
  1. 先看用户的要求，再看已经完成了哪些步骤。
  2. 如果资料还没查过，先派 researcher。
  3. 资料查完后，派 writer 整理成文。
  4. 都完成了，返回 FINISH。

已完成：{done}
"""
```

四个要点：

| 要点 | 为什么 |
|---|---|
| 明确"自己不要动手做事" | 否则主管会尝试直接回答，绕过专家 |
| 逐个说明专家的职责 | 主管靠这个做路由决策 |
| 把终止条件写死 | 防止无限循环 |
| 注入"已完成"清单 | 防止重复派活（**最容易漏的一条**） |

### 3.2 用结构化输出限制选择范围

```python
class Route(BaseModel):
    next: Literal["researcher", "writer", "FINISH"]
    reason: str

router = llm.with_structured_output(Route)
decision = router.invoke(messages)
print(decision.next)     # 保证是三者之一
```

**为什么必须用结构化输出？**

如果让模型输出自由文本，你得去解析 "我认为应该派 researcher 去处理" —— 脆弱且易错。
`Literal` 把模型的输出**限制在枚举值里**，这是"让 LLM 输出可控"的最实用手段。

### 3.3 专家就是 ReAct 子图

```python
def make_worker(name, system_prompt, tools):
    worker_llm = get_model().bind_tools(tools)

    def agent(state):
        messages = [SystemMessage(content=system_prompt)] + state["messages"]
        return {"messages": [worker_llm.invoke(messages)]}

    return (
        StateGraph(WorkerState)
        .add_node(name, agent)
        .add_node("tools", ToolNode(tools))
        .add_edge(START, name)
        .add_conditional_edges(name, tools_condition, {"tools": "tools", "__end__": END})
        .add_edge("tools", name)
        .compile(name=name)
    )
```

**注意：它就是第 02 课那八行代码封装成的函数。** 多智能体一点不神秘——
每个"专家"都是你早就写过的 ReAct 图，只是被挂到了父图的节点上。

### 3.4 状态怎么共享

```python
class SupervisorState(TypedDict):
    messages: Annotated[list, add_messages]   # 大家都往这里写
    next: str                                  # 主管的决策
    done: Annotated[list, merge_unique]        # 已完成清单
```

- **共享 `messages`**：主管能看到所有专家干了什么，专家能看到用户的要求和其他人的产出
- **`done` 用去重 reducer**：避免重复记录

第 08 课"子图用法 A"的知识用在这里：**子图状态是父图状态的子集**，就能直接挂上去。

## 四、多智能体的常见坑

| 坑 | 症状 | 解决 |
|---|---|---|
| **无限循环** | `GraphRecursionError` | 加终止条件；状态里记 `done`；设 `recursion_limit` |
| **主管抢活干** | 主管自己回答了，专家没用上 | 提示词里强调"你自己不要动手" |
| **专家没有产出** | 主管不知道该收尾了 | 要求专家必须写一条总结消息 |
| **上下文爆炸** | token 消耗暴涨 | 给专家传"摘要"而不是完整历史；或给每条消息加截断 |
| **重复派活** | 同一个专家被派了三次 | 状态里记录 `done` |
| **主管决策不稳定** | 同样输入，有时派 A 有时派 B | 用结构化输出 + 温度调 0 |

### 4.1 上下文管理是个真问题

多智能体最容易忽视的成本：**每个专家的每次调用都要带上完整对话历史**。

```
    主管决策 1 次       + 完整历史
    专家 A 执行 2 次    + 完整历史 × 2
    主管决策 2 次       + 完整历史
    专家 B 执行 2 次    + 完整历史 × 2
    ...
```

轮次多了，token 消耗是**平方级**增长的。

**对策**：
- 专家只传它需要的片段（用 `Send` 或子状态）
- 对历史做摘要压缩
- 给专家加"只看最近 N 条"的裁剪

## 五、选型决策树

```
    任务能被固定顺序拆成几步吗？
        │
        ├─ 能 → 用普通节点串联/并行（第 07 课）
        │        别引入多智能体，省事又省钱
        │
        └─ 不能，需要动态决定下一步找谁
              │
              ├─ 调度逻辑简单、规则明确
              │     → 用条件边写个路由函数就够了
              │
              ├─ 需要语义理解来决策
              │     → Supervisor + with_structured_output ★推荐
              │
              ├─ 任务规模很大，需要分组管理
              │     → 层级式（Supervisor 套 Supervisor）
              │
              └─ 需要自由讨论、角色边界模糊
                    → 网络式（Command(goto=...) handoff）
```

## 六、小结

| 架构 | 特点 | 适用 |
|---|---|---|
| 网络式 | 专家互相 handoff，无中心 | 自由讨论、辩论 |
| **主管式** | **中心调度，路径可控** | **绝大多数场景** |
| 层级式 | 主管套主管 | 大型任务、分组管理 |
| 流水线 | 固定顺序，无调度 | 流程确定的场景（其实不算多智能体） |

**三条核心认知**：

1. **多智能体是权衡，不是升级。** 简单方案能解决就别上它。
2. **专家就是 ReAct 子图。** 你已经会写了（第 02 + 08 课）。
3. **主管靠结构化输出做决策，靠 `done` 字段防重复，靠 `recursion_limit` 兜底。**
