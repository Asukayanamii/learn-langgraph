# 原理篇（三）：持久化（Checkpointer）与中断（interrupt）

> 对应课程：**第 03 课**、**第 04 课**、**第 08 课**
>
> 这两件事经常被分开讲，但它们其实是**同一个机制的两面**：
> 中断之所以能成立，正是因为状态被持久化了。

---

## 一、记忆的真相：它不是模型的能力

### 1.1 先破除误解

很多人以为"给模型传 messages 列表"就等于有记忆。其实：

```
    传给模型的 messages  =  "这一次请求里带了什么"
                              ↓
                           请求结束就没了

    真正的记忆           =  "把每一步的状态存下来，下次再拼回去"
                              ↓
                           这是**存储问题**，不是模型问题
```

**推论：所谓"记忆"，本质是状态持久化。** 这也是为什么 LangGraph 能把记忆做得这么轻——
因为它本来就在管理状态。

### 1.2 没有持久化会怎样

```python
# 每一轮都是独立的一次 invoke
app.invoke({"messages": [{"role": "user", "content": "我叫小明"}]})
# → 状态里只有 2 条消息

app.invoke({"messages": [{"role": "user", "content": "我叫什么？"}]})
# → 状态里还是只有 2 条消息，模型根本不知道"小明"是谁
```

第 03 课的"实验一"就是这个对照组的失败现场。

## 二、Checkpointer 的工作原理

### 2.1 核心结构：三层

```
    ┌─────────────────────────────────────────────────────────────┐
    │  Thread（会话）                                              │
    │  用 thread_id 标识，比如 "user-42"、"session-1"              │
    │                                                             │
    │   ┌─────────────────────────────────────────────────────┐   │
    │   │  Checkpoint（检查点 = 一份完整状态快照）               │   │
    │   │  用 checkpoint_id 标识，每个超级步之后存一份           │   │
    │   │                                                     │   │
    │   │   checkpoint_1  {messages: [用户:你好]}              │   │
    │   │   checkpoint_2  {messages: [用户:你好, AI:你好呀]}    │   │
    │   │   checkpoint_3  {messages: [..., 用户:我叫小明]}      │   │
    │   │   checkpoint_4  {messages: [..., AI:记住啦]}         │   │
    │   │        ▲                                            │   │
    │   │        └── 每个 checkpoint 都记录了 parent_id，       │   │
    │   │            所以能串成一条时间线（这就是"历史"）        │   │
    │   └─────────────────────────────────────────────────────┘   │
    └─────────────────────────────────────────────────────────────┘
```

### 2.2 一次 `invoke` 的完整生命周期

```
    app.invoke(input, config={"configurable": {"thread_id": "t1"}})
        │
        ├─ 1. 取出该 thread 下**最新**的 checkpoint
        │     → 得到"上次结束时的状态"
        │
        ├─ 2. 用新输入和这个状态做一次**合并**
        │     → 新输入里的 messages 会被 add_messages 追加到历史后面
        │
        ├─ 3. 从合并后的状态开始跑图
        │
        ├─ 4. 每跑完一个超级步 → 存一份新的 checkpoint
        │     （记录：通道值、版本号、下一步要去哪、parent_id）
        │
        └─ 5. 跑完 → 返回最终状态
```

**关键点在第 1、2 步**：所谓"记住上一轮"，就是"把旧状态取出来，和新输入合并"。

### 2.3 checkpoint 里存了什么

一个 checkpoint 不只是"状态值"，还包含：

| 内容 | 作用 |
|---|---|
| 各通道的值 | 状态本身 |
| 各通道的版本号 | 处理并发写入（同一轮多个节点写同一字段） |
| `next` | 接下来要执行哪些节点 → **中断恢复靠它** |
| `parent_id` | 指向上一个 checkpoint → **历史链靠它** |
| `metadata.step` | 这是第几个超级步 → 便于展示和理解 |
| `pending_writes` | 本轮已产生但还没合并的写入 |

**为什么这些都要存？** 因为恢复执行时必须知道"我跑到哪了、还有谁没跑"。

### 2.4 三种后端，一套接口

```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.checkpoint.sqlite import SqliteSaver
# from langgraph.checkpoint.postgres import PostgresSaver

app = builder.compile(checkpointer=InMemorySaver())    # 内存：进程结束就没了
app = builder.compile(checkpointer=SqliteSaver(...))   # 本地文件：单机持久
app = builder.compile(checkpointer=PostgresSaver(...)) # 数据库：多实例共享
```

因为接口一致（都实现 `BaseCheckpointSaver`），**业务代码一行都不用改**。

> ⚠️ 生产环境为什么必须用 `PostgresSaver` 这类共享存储？
> 因为如果你的服务跑在 3 个实例上，每个实例各写各的本地 SQLite 文件，
> 用户的请求被负载均衡打到哪个实例，看到的历史就完全不一样了。

### 2.5 `thread_id` 的作用

```python
config_a = {"configurable": {"thread_id": "user-alice"}}
config_b = {"configurable": {"thread_id": "user-bob"}}
```

`thread_id` 是**会话隔离的唯一依据**：

- 同一个 `thread_id` → 共享同一份历史（相当于同一个对话窗口）
- 不同的 `thread_id` → 完全隔离，互不干扰

第 03 课的"实验二"演示了这个隔离：会话 A 记得"小明"，会话 B 完全不知道。

## 三、`interrupt()` 的工作原理

### 3.1 为什么必须有 checkpointer

因为"暂停"要成立，必须做到两件事：

1. **把当前的完整状态存下来** —— 否则恢复时不知道从哪继续
2. **记住"接下来要执行哪个节点"** —— 这就在 checkpoint 的 `next` 字段里

**所以：`interrupt` 和 `checkpointer` 是绑定的。** 没有 checkpointer，中断无从谈起。

### 3.2 三步原理

```python
def approval_node(state):
    # (A) 图执行到这里，调用 interrupt()
    decision = interrupt({"question": "是否允许发送邮件？"})

    # (C) 【恢复时】图会从函数开头重新执行，
    #     interrupt() 这次直接返回人类给的答案，然后继续往下跑
    return {"approved": bool(decision)}
```

```
    ① 暂停
       interrupt(payload) 在内部抛出一个 GraphInterrupt 异常
            ↓
       这个异常被引擎捕获（不是真的报错）
            ↓
       引擎把当前状态 + next=('approval',) 存成 checkpoint
            ↓
       把 payload 作为返回值交给调用方

    ② 等待
       调用方拿到 {"__interrupt__": [Interrupt(value=payload)]}
       —— 程序可以去做任何事：弹窗、发通知、等三小时

    ③ 恢复
       app.invoke(Command(resume=答案), config=config)
            ↓
       引擎从 checkpoint 里读出 next=('approval',)
            ↓
       ★★ 重新执行 approval 节点（从头开始，不是从中间）
            ↓
       这次执行到 interrupt() 时，它不再暂停，而是直接返回"答案"
            ↓
       节点继续往下跑完
```

### 3.3 最重要的一条推论

> **`interrupt()` 之前的代码会被执行两次。**

因为恢复时节点是"重放"而不是"续跑"。所以：

```python
# ❌ 危险的写法
def bad_node(state):
    send_email_to_admin()                  # ← 会执行两次！发两封邮件！
    decision = interrupt("确认吗？")
    ...

# ✅ 正确的写法
def good_node(state):
    decision = interrupt("确认吗？")        # ← interrupt 放最前面
    send_email_to_admin()                  # ← 只会在恢复后执行一次
    ...
```

**规矩：`interrupt()` 之前绝对不能有副作用。**

### 3.4 调用方怎么处理中断

**方式一：`invoke` —— 检查返回值里有没有 `__interrupt__`**

```python
result = app.invoke(input, config=config)
if "__interrupt__" in result:
    payload = result["__interrupt__"][0].value
    # 去做人机交互...
    result = app.invoke(Command(resume=answer), config=config)
```

**方式二：`stream` —— 中断会作为一个事件出现**

```python
for event in app.stream(input, config=config, stream_mode="updates"):
    if "__interrupt__" in event:
        payload = event["__interrupt__"][0].value
```

**方式三：直接查状态**

```python
snapshot = app.get_state(config)
if snapshot.next:                      # 有 next → 说明图没跑完，停住了
    for task in snapshot.tasks:
        for intr in task.interrupts:
            print(intr.value)
```

实战项目 `capstone/assistant.py` 用的是方式二，因为它在流式输出。

### 3.5 静态断点 vs 动态中断

| | 静态断点 | 动态中断 |
|---|---|---|
| 写法 | `compile(interrupt_before=["tools"])` | 节点内调 `interrupt(payload)` |
| 触发时机 | 编译期写死，到了必停 | 运行时判断，可以条件触发 |
| 能否带上下文 | 不能（只知道"要执行 tools 了"） | 能，payload 可以是任意对象 |
| 适用场景 | 调试、每步都要人确认 | 生产环境的审批流 |

**结论：生产环境用动态 `interrupt()`**，因为你必须告诉审批人"到底要做什么"。

## 四、时间旅行：快照带来的额外能力

一旦有了完整的状态快照，你能做的事情远不止"记忆"。

### 4.1 回看历史

```python
for snapshot in app.get_state_history(config):
    print(snapshot.metadata["step"], snapshot.values, snapshot.next)
```

因为每个 checkpoint 都记录了 `parent_id`，引擎能沿着链条一路回溯。

### 4.2 人工修改状态

```python
app.update_state(config, {"total": 999, "log": ["【人工修改】"]})
```

**它会生成一份新的 checkpoint**，原有历史不受影响。这在真实场景里非常有用：

```
    模型答错了一步 → 人工改掉那条错误消息 → invoke(None, config) 让它接着往下跑
    （不用从头再来，省时省钱）
```

### 4.3 从某个历史点重放（开分支）

```python
# 拿到某份历史快照的 config（里面带着 checkpoint_id）
fork_config = history[-3].config

# 直接拿它去 invoke —— 会从那个时刻往后跑，并写成一条新分支
result = app.invoke({"total": 0}, config=fork_config)
```

第 08 课实验里，我们先跑到 `total=20`，再把当前状态改成 `999`，
然后从最早那份快照重放，得到了一个全新的 `20`——**原历史完好无损。**

### 4.4 为什么这对生产系统很重要

| 场景 | 没有快照 | 有快照 |
|---|---|---|
| 模型答错了 | 只能整个重跑 | 改一步接着跑 |
| 排查线上问题 | 猜当时看到了什么 | 回放到那一刻看 |
| 用户投诉"你上次说的不对" | 无据可查 | 调出完整记录 |
| 需要人工审批 | 得额外做一套状态机 | `interrupt` 直接支持 |
| 部署了新版本想对比 | 没法对比 | 同一起点跑两条分支 |

**这就是为什么 LangGraph 敢用在金融、医疗、客服这类严肃业务里。**

## 五、实战模式：这三种能力怎么组合使用

以 `capstone/assistant.py` 为例：

```python
# ① 持久化：记忆落在磁盘上，关掉程序再打开还在
with SqliteSaver.from_conn_string(str(db_path)) as checkpointer:
    app = build_assistant(checkpointer)

    # ② 会话隔离：每个会话一个 thread_id
    ask(app, "我叫小明", thread_id="session-1")
    ask(app, "我叫什么", thread_id="session-1")   # → 记得
    ask(app, "我叫什么", thread_id="session-2")   # → 不知道

    # ③ 人工审批：危险操作前暂停
    #    approval 节点里 interrupt()，调用方拿到 payload 问用户，再 Command(resume=...)
```

三个能力**共用一个机制**：状态快照。

## 六、小结

| 概念 | 要点 |
|---|---|
| 记忆的本质 | 状态持久化，不是模型能力 |
| Checkpoint | 一份完整状态快照，含通道值 + 版本号 + `next` + `parent_id` |
| Thread | 用 `thread_id` 隔离的会话 |
| 挂载方式 | `compile(checkpointer=...)`，图结构不用改 |
| `interrupt()` | 抛异常暂停 → 存 checkpoint → 恢复时**重放节点** |
| 铁律 | `interrupt()` 之前不能有副作用（会被执行两次） |
| 恢复方式 | `Command(resume=值)` |
| 前提 | 必须配 checkpointer |
| 时间旅行 | `get_state_history` / `update_state` / 用旧 config 重放 |
