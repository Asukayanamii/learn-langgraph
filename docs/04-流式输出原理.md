# 原理篇（四）：流式输出的原理

> 对应课程：**第 06 课**
>
> 这篇文档回答：**"一个字一个字冒出来"在技术上是怎么实现的？四种 stream_mode 分别适合什么场景？**

---

## 一、为什么必须流式

先算一笔"体感账"：

```
    不流式：
        用户按回车 ────────────────────────────────▶ 8 秒后一次性出现
                    （界面完全没反应，用户以为卡死了）

    流式：
        用户按回车 ─▶ 首字 ─▶ 字 ─▶ 字 ─▶ 字 ─▶ 完成
                    0.3 秒就开始有反馈
```

**总耗时可能一模一样，但用户对"反应快慢"的感知完全由"首字出现时间"决定。**

这就是为什么所有 LLM 产品都在做流式。

---

## 二、流式的数据从哪来

LangGraph 的流式之所以能做得好，是因为它的执行模型天然提供了"分步产出"的机会。

```
    图是一个节点一个节点跑的
              ↓
    每跑完一个节点，引擎就有一个"交出中间结果"的机会
              ↓
    这就产生了 values / updates 两种流

    而节点内部调模型时，模型本身是逐 token 生成的
              ↓
    给它挂个回调，token 一产生就推送
              ↓
    这就产生了 messages 流

    节点还可以主动往外推自定义事件
              ↓
    这就产生了 custom 流
```

## 三、四种 stream_mode 详解

### 3.1 `values` —— 每一步之后的完整状态

```python
for snapshot in app.stream(input, stream_mode="values"):
    print(snapshot)   # 每一步之后的**完整** state
```

返回形状：`dict`（状态字典）

```
    {"messages": [用户:你好]}                                 ← 第 0 步
    {"messages": [用户:你好, AI:你好呀]}                       ← 第 1 步
    {"messages": [用户:你好, AI:你好呀, 用户:天气]}             ← 第 2 步
```

**用途**：调试状态演化，看"数据是怎么一点点长大的"。

**缺点**：数据量大（每步都是全量），带上下文长对话时不适合推给前端。

### 3.2 `updates` —— 每一步的增量（最常用）

```python
for event in app.stream(input, stream_mode="updates"):
    print(event)   # {节点名: 该节点返回的更新}
```

返回形状：`dict[str, dict]`

```
    {"agent": {"messages": [AIMessage(...)]}}
    {"tools": {"messages": [ToolMessage(...)]}}
    {"agent": {"messages": [AIMessage(...)]}}
```

**用途**：
- 显示"正在进行哪一步"（"正在查询知识库…"）
- 记录执行日志
- 在前端画流程进度条

**这是最实用的模式**，因为它直接告诉你"谁执行完了、改了什么"。

### 3.3 `messages` —— 逐 token 输出

```python
for chunk, metadata in app.stream(input, stream_mode="messages"):
    print(chunk.content, end="", flush=True)
```

返回形状：`tuple[AIMessageChunk, dict]`

```
    (AIMessageChunk(content="Lang"), {"langgraph_node": "chatbot", "tags": [...]})
    (AIMessageChunk(content="Graph"), {"langgraph_node": "chatbot", ...})
    ...
```

**为什么返回的是二元组而不是单独的 chunk？**

因为**一张图里可能有多个模型调用**（agent 节点调一次、另一个节点又调一次）。
`metadata` 里的 `langgraph_node` 告诉你"这段文字是哪个节点产生的"，
这样前端才能把它显示在正确的气泡里。

**用途**：打字机效果。

**注意**：这条路走的是模型的流式接口。如果模型不支持流式（或参数没开），
你会一次性拿到一个完整的 chunk，而不是逐 token。

### 3.4 `custom` —— 节点自己发射的数据

```python
from langgraph.config import get_stream_writer

def my_node(state):
    writer = get_stream_writer()          # 拿到"发射器"
    for i, step in enumerate(steps, 1):
        do_work(step)
        writer({"progress": i / len(steps), "step": step})   # 推给调用方
    return {...}
```

```python
for chunk in app.stream(input, stream_mode="custom"):
    print(chunk)      # 就是 writer() 里传的对象，原样到达
```

**它的价值**：节点内部那些"模型和状态都不知情"的过程信息，终于能被看见了。

例如：
- 一个循环跑了 10 轮的 agent，每轮推送 `{"round": n}`
- 一个长任务推送 `{"progress": 0.6, "stage": "解析文档"}`
- 推送中间结果给前端做"边生成边展示"

**注意**：`get_stream_writer()` 拿到的是一个"从当前运行时上下文里取出来的"写入器。
它在节点函数内部调用才有效，脱离运行时上下文会拿不到东西。

## 四、同时订阅多种流

```python
for mode, chunk in app.stream(input, stream_mode=["updates", "messages"]):
    if mode == "updates":
        ...   # chunk 是 {节点名: 更新}
    elif mode == "messages":
        ...   # chunk 是 (AIMessageChunk, metadata)
```

**规则：`stream_mode` 传列表时，返回值一定变成 `(模式名, 数据)` 元组。**

这条规则不要记错——很多人第一次用会以为还是原来那种形状。

**实战意义**：Web 服务里一个 SSE 接口可以同时推"进度事件"和"token"，前端一次连接拿全部信息。

## 五、一个可以直接抄走的流式聊天函数

```python
def streaming_chat(app, user_input, config=None):
    full_text = []
    print("AI > ", end="", flush=True)

    for chunk, metadata in app.stream(
        {"messages": [HumanMessage(content=user_input)]},
        config=config,
        stream_mode="messages",
    ):
        if chunk.content:
            print(chunk.content, end="", flush=True)
            full_text.append(str(chunk.content))

    print()
    return "".join(full_text)     # 返回完整文本，方便调用方存库
```

三个设计要点：

1. **`end=""` + `flush=True`** —— 不换行、立刻刷出，否则缓冲区会攒着一起输出
2. **同时累积 `full_text`** —— 流式显示完了，调用方往往还需要完整文本（存库、发通知）
3. **返回而非仅打印** —— 让"显示"和"使用"解耦

## 六、异步版本

在 Web 服务里，几乎一定要用异步版本：

```python
async def stream_chat(app, user_input, config):
    async for chunk, metadata in app.astream(
        {"messages": [HumanMessage(content=user_input)]},
        config=config,
        stream_mode="messages",
    ):
        if chunk.content:
            yield chunk.content          # 直接 yield 给 SSE / WebSocket
```

对应关系：

| 同步 | 异步 |
|---|---|
| `invoke` | `ainvoke` |
| `stream` | `astream` |
| `get_state` | `aget_state` |
| 节点函数 | 可以是 `async def` |
| `ToolNode` | 自动支持异步工具 |

**LangGraph 会自动处理同步/异步混合**：如果你用 `astream`，它会用异步路径执行；
节点函数是同步的也没关系（会在线程池里跑）。但为了性能，生产环境建议全异步。

## 七、常见坑

| 现象 | 原因 | 解决 |
|---|---|---|
| 输出一坨，不是逐字 | 没加 `flush=True` | 加 `flush=True` |
| 拿不到 token，只有一个大 chunk | 模型不支持流式 / 走了非流式路径 | 检查模型配置；本项目的离线模型已实现 `_stream` |
| `mode, chunk` 解包报错 | `stream_mode` 传了列表，返回变成元组 | 要么传字符串，要么按元组解包 |
| `custom` 收不到东西 | `get_stream_writer()` 在节点外调用 | 必须在节点函数内部调用 |
| 只看到工具结果，看不到思考过程 | 工具节点没有模型调用 | 正常现象，模型只在 agent 节点产生 token |

---

## 八、小结

| 模式 | 返回形状 | 用途 |
|---|---|---|
| `values` | `dict` | 调试状态演化 |
| `updates` | `dict[str, dict]` | **进度提示、执行日志（最常用）** |
| `messages` | `(AIMessageChunk, metadata)` | **打字机效果** |
| `custom` | 任意对象 | **自定义进度、中间事件** |

**核心认知**：流式不是"额外加的功能"，而是图**分步执行**这一特性的自然产物。
理解了超级步，就理解了为什么 `updates` 和 `values` 能存在。
